# Meditour 产品与工程路线图

## 1. 项目定位

### 对外定位

面向国际游客的中国旅行助手，帮助用户在出发前完成目的地发现和行程规划，在旅途中解决交通、支付、语言和本地服务问题。

医疗服务不是首页主业务，也不作为品牌的第一认知。它只作为用户主动进入的增值协助入口，提供合规的信息对接和人工协调，不提供线上诊断、疗效承诺或未经许可的医疗交易。

### 核心价值

- 出发前：降低信息分散和语言差异带来的规划成本。
- 旅途中：提供真正可执行的行程和常用工具。
- 服务侧：将有明确意向的用户连接给合规的本地合作方。
- 增值侧：在用户主动提出时提供健康与医疗协助。

### 品牌决策

`Meditour` 的名称天然偏向医疗，与“旅游优先”的定位存在冲突。首个可用版本可以保留现名，但在公开推广前应验证一个更中性的消费者品牌；`Meditour` 可以保留为公司名或健康服务子品牌。

## 2. 当前阶段判断

当前版本属于 UI 原型，已经具备：

- Flutter 多端基础工程。
- 首页、目的地详情、旅行工具、医疗列表、服务详情和预约表单。
- `en`、`zh`、`de`、`fr` 四种界面语言。
- GoRouter 路由、Provider 状态管理和语言持久化。
- “发现、行程、旅行工具、我的”四栏主框架。
- 目的地多语言关键词搜索、收藏筛选和本地持久化。
- 行程创建、编辑、删除和本地持久化。
- Git 远程仓库与 GitHub Actions 基础 CI。
- 基础视觉规范和可复用组件。

尚未形成可用产品闭环：

- 目的地和服务数据是内存中的示例数据。
- 签证、交通、支付和网络工具目前只有基础内容，酒店入口尚未接入。
- 行程尚不支持按天安排、地点排序、分享和离线内容包。
- 预约表单只生成本地编号，没有提交到后台。
- 没有账号、订单或咨询状态、消息通知和客服衔接。
- 旅游内容没有完整覆盖四种语言。
- 没有内容管理后台、数据分析、异常监控和发布流程。
- 自动化测试已覆盖主导航、搜索收藏和行程持久化，但覆盖面仍有限。

因此近期目标不是继续堆叠静态页面，而是完成一个能够被真实用户使用和度量的最小闭环。

## 3. 首个可用闭环

目标用户完成以下流程，才算进入 MVP：

1. 选择语言、旅行时间、预算和兴趣。
2. 搜索并收藏中国目的地。
3. 创建一份可编辑的多日行程。
4. 查看交通、支付、签证和常用语等旅行工具。
5. 保存或分享行程。
6. 提交定制行程或本地服务咨询。
7. 后台收到咨询并更新处理状态。

建议主导航设置为：

- 发现
- 行程
- 旅行工具
- 我的

健康服务放在“我的 > 更多协助 > 健康服务”或旅行详情中的主动帮助入口，不进入主导航，不在首页占据核心推荐位。

## 4. 功能优先级

### P0：工程基线，3 至 5 天

- 初始化 Git 仓库和远程托管，建立 `main` 与功能分支流程。
- 更新 README、环境说明、产品路线图和发布说明。
- 修正 `respositories` 等目录命名问题。
- 增加统一错误处理、日志和环境配置。
- 建立静态检查、单元测试和构建 CI。
- 清理生成文件、日志和临时设计稿的版本控制范围。
- 明确隐私政策、用户协议和内容来源要求。

验收标准：新成员能在 30 分钟内启动项目；每次提交自动执行 analyze 和 test。

### P1：旅游 MVP，2 至 3 周

- 建立四栏应用主框架。
- 将目的地扩充到 8 至 12 个核心城市。
- 完成四语言目的地内容、搜索、季节和兴趣筛选。
- 增加收藏和最近浏览，支持本地持久化。
- 完成行程创建、按天编辑、地点排序和备注。
- 将签证、支付、交通、网络和常用语入口做成真实内容。
- 增加定制行程咨询表单，并实际保存咨询记录。
- 增加空状态、加载状态、错误状态和无网络状态。

验收标准：用户不依赖开发者讲解，可以独立生成并保存一份中国旅行行程。

### P2：服务闭环，3 至 4 周

- 接入后端数据库、身份认证和对象存储。
- 建立目的地、景点、行程、收藏、咨询和合作方数据模型。
- 提供轻量内容管理后台，运营人员可更新多语言内容。
- 增加咨询状态、邮件或消息通知和人工客服分配。
- 增加可分享的 Web 行程页面。
- 接入产品分析和崩溃监控。
- 健康协助采用独立授权、独立隐私提示和人工审核。

验收标准：从用户提交到合作方处理可以被跟踪，运营人员无需修改代码即可更新内容。

### P3：公开测试，2 至 3 周

- 部署公开 Web/PWA 演示站并绑定正式域名。
- 完成 Android 内测包和 iOS TestFlight。
- 完成响应式、可访问性、性能和弱网测试。
- 准备应用图标、商店截图、介绍视频和客服渠道。
- 发布隐私政策、用户协议、免责声明和数据删除入口。
- 邀请首批 100 名目标用户进行封闭测试。

验收标准：核心流程无阻断，关键事件可统计，用户反馈有固定处理机制。

### P4：商业化验证，4 至 8 周

- 接入持牌旅行社、当地向导、票务、酒店、交通和 eSIM 合作方。
- 测试定制行程服务费、合作佣金和企业客户方案。
- 增加合作方后台和结算对账。
- 根据数据决定是否接入支付和正式上架应用商店。
- 健康服务只与具备资质的机构合作，并由法律和合规人员审查流程。

验收标准：至少有一种收入模式得到真实付费验证，而不是只依赖下载量。

## 5. 目标工程结构

采用按业务功能拆分的渐进式结构，不需要一次性重写：

```text
lib/
  app/
    app.dart
    bootstrap.dart
    router.dart
  core/
    analytics/
    config/
    errors/
    localization/
    network/
    storage/
  features/
    discover/
      data/
      domain/
      presentation/
    itinerary/
      data/
      domain/
      presentation/
    travel_tools/
      data/
      domain/
      presentation/
    account/
      data/
      domain/
      presentation/
    consultation/
      data/
      domain/
      presentation/
    health_assistance/
      data/
      domain/
      presentation/
  shared/
    models/
    widgets/
  l10n/
```

工程原则：

- 保留 Provider，按功能建立独立 Controller，暂不为更换状态管理方案增加风险。
- 页面只负责渲染和交互，不直接依赖静态仓库或网络实现。
- Domain 层定义实体和仓库接口，Data 层实现远程与本地数据源。
- SharedPreferences 只保存语言和轻量设置；收藏、行程和离线内容使用结构化本地数据库。
- 界面固定文案使用 AppLocalizations；目的地等运营内容使用后端多语言字段。
- 所有网络操作提供 loading、error、retry 和离线降级。
- 每个核心功能至少包含业务单元测试、Repository 测试和关键 Widget 测试。

## 6. 后端与数据建议

MVP 阶段优先使用托管后端快速验证，例如 Supabase：

- PostgreSQL 保存目的地、行程、咨询和合作方数据。
- Auth 提供邮箱或第三方登录。
- Storage 保存内容图片。
- Edge Function 处理通知和受保护操作。
- Row Level Security 隔离用户数据。

早期只保存旅行资料和普通联系方式，不收集病历、检查报告等敏感医疗数据。若后续确需处理，应单独完成 GDPR、中国个人信息保护法、数据跨境和医疗数据合规评估。

面向中国境内长期运营前，需要评估域名备案、节点可用性和数据存放位置。MVP 后端的调用应封装在 Repository 后面，以便后续迁移。

## 7. 商业模式验证

按风险从低到高验证：

1. 免费旅行工具获取用户和需求数据。
2. 收费定制行程和人工旅行顾问。
3. 酒店、票务、交通、eSIM 和当地体验合作佣金。
4. 为入境游机构提供多语言获客和 SaaS 工具。
5. 合规健康协助服务费或机构合作费。

首阶段不建议自营打包旅游产品或直接销售医疗服务。涉及旅行社业务、支付、保险和医疗服务时，应先由持牌合作方承接。

## 8. 融资前必须积累的数据

投资人更关心验证结果，而不是页面数量。建议至少连续记录四周：

- 访谈过的目标游客数量。
- 完成首次行程创建的用户比例。
- 每位用户创建或收藏的目的地数量。
- 7 日和 30 日留存。
- 行程分享率。
- 定制咨询提交率。
- 有效咨询到合作成交的转化率。
- 人工响应时间和用户满意度。
- 每个获客渠道的成本。

建议首轮验证目标：

- 访谈 30 至 50 名计划来华的国际游客。
- 获得 100 至 300 名封闭测试用户。
- 获得至少 3 家入境游或本地服务合作意向。
- 完成至少 10 个真实咨询，并验证其中一种付费方式。

## 9. 对外融资材料

公开寻找投资与合作前准备：

- 可直接访问的 Web/PWA 演示地址。
- 90 秒核心流程演示视频。
- 8 至 10 页融资演示文稿。
- 一页项目介绍和合作需求。
- 用户访谈、测试数据和关键指标看板。
- 产品路线图、商业模型和资金用途。
- 团队介绍、股权结构和知识产权说明。
- 合作意向书、隐私政策、用户协议和合规说明。
- 整洁的私有代码仓库、发布记录和测试报告。

融资演示文稿顺序：

1. 入境中国游客面临的具体问题。
2. 明确的目标用户和使用场景。
3. 产品演示和核心闭环。
4. 市场规模及增长依据。
5. 竞争方案和差异化。
6. 获客与合作方策略。
7. 商业模式。
8. 已验证的数据和案例。
9. 团队与执行计划。
10. 融资金额、出让方案和资金用途。

## 10. 合规底线

- 不宣传疗效，不做线上诊断，不暗示平台替代医生。
- 健康入口必须由用户主动进入，并展示独立授权和免责声明。
- 联系方式、护照、健康信息和支付信息按敏感等级分开处理。
- 默认最小化采集数据，并提供导出和删除渠道。
- 所有图片、城市内容、地图和翻译内容必须确认授权或来源。
- 实际销售旅游产品时由持牌旅行社承接。
- 正式开放医疗协助前，由目标市场和服务所在地的专业律师审查。

## 11. 下一迭代建议

当前已完成 Git/CI、四栏主框架、目的地搜索收藏和首个本地行程创建流程。下一轮继续完成 P1 的可执行行程：

1. 增加按天行程安排、地点排序和每日备注。
2. 从目的地详情将体验直接加入指定行程。
3. 扩充到 8 至 12 个核心城市并补齐四语言运营内容。
4. 完善签证、支付、交通、网络和常用语内容及来源日期。
5. 增加行程分享、导出和离线查看。
6. 建立定制行程咨询记录，并为后端接入预留 Repository 接口。

完成以上内容后，用户可以独立生成、保存并使用一份中国旅行行程，再接后端和公开测试更合理。
